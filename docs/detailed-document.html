1 · Where this came from

  • Original build: ET AI Hackathon 2026, Problem #4 — "AI Intelligence Platform for Data-Centre EPC Project Delivery." EPC = Engineering, Procurement, Construction — the industry term for how a big facility (a data centre, in this case) actually gets built by a web of contractors, submittals, inspections, and sign-offs.
  • That hackathon ended. The project then moved to HexaFalls, an open-innovation hackathon with sponsor prize tracks and no fixed problem statement.
  • What changed: the positioning broadened from "just data centres" to any hyperscale or public-infrastructure megaproject — semiconductor fabs, highways, metro rail, government buildings — anywhere a lot of money moves through a paper trail that's hard for any one person to audit.
  • What did NOT change: the core credibility idea (next section). Every HexaFalls addition sits around that core — none of it replaces or weakens it.

2 · The one idea that makes this different

The problem with most "AI compliance" tools: they either (a) let the AI just say "this passes" or "this fails" with no way to check its work, or (b) they cite a rule but you have no way to know if the rule is real or made up.

SiteMind's answer: the LLM never computes a verdict.
The AI's job is only to read and explain. Every pass/fail decision is made by plain, ordinary computer code — the kind you could open and read line by line — checking a number against a real, citable rule from an actual government/industry standard.

  • Why this matters: if a verdict is ever wrong, you can point at the exact line of code that produced it and the exact clause it checked against — nothing is hidden inside a black-box model's "trust me."
  • Every citation is real — pulled from real, digitised Indian building-code documents (IS 456, IS 1893, IS 875, CEA regulations, etc.), never invented from the AI's training memory.
  • Every number this project claims is backed by a real, re-runnable test (an "eval" — see the Glossary) — nothing is just asserted in a slide.

3 · The five original pillars

Think of these as five separate mini-products bundled into one app, all reading from the same project's documents.

① Compliance Agent — the flagship

  • What it does: you upload a design document (a "Design Basis Report" or a contractor submittal). It reads out every checkable engineering value (concrete grade, rebar cover, seismic factor, etc.) along with the exact sentence it came from, then checks each one against the real building code clause that governs it.
  • Output: a list of "NCRs" (Non-Conformance Reports) — plain-English findings, each with severity, the exact clause cited, and a recommended fix.
  • Who uses it: a QA/QC manager or design reviewer on a construction project, who today does this checking by hand against a stack of paper codes.
  • Real-world scenario: a structural engineer submits a foundation drawing specifying 30mm of concrete cover. SiteMind reads that value, finds the sentence it came from, checks it against IS 456's real minimum-cover table for that exposure condition, and — in this project's demo dataset — correctly flags it as short of the 50mm required, citing the exact clause number.

② Project / RFI Copilot

  • What it does: a search-and-answer box for the whole project — ask a question in plain English, get an answer with citations, not a guess.
  • The safety mechanism: if the system isn't confident enough in what it found, it says so honestly ("no confident answer") instead of inventing something plausible-sounding.
  • Bonus: it can also recognize when a question is basically a duplicate of an already-answered RFI (Request for Information) — even if worded completely differently.
  • Who uses it: anyone on the project team who'd otherwise have to dig through hundreds of pages of specs to answer "what's the required clearance for X?"

③ Schedule Risk

  • What it does: looks at the project's construction schedule (a network of hundreds of dependent tasks) using a real scheduling technique called CPM (Critical Path Method — basically: which tasks, if delayed, delay the WHOLE project), combined with leading-indicator rules (a late procurement order, a stretch of bad weather, a workforce shortage) to predict which activities are at risk of slipping.
  • Output: a risk list with WHY each activity is at risk, how many days it might slip, and — critically — how that slip would ripple through the rest of the schedule, plus AI-generated mitigation suggestions from three different "angles" (procurement, scheduling float, and resourcing).
  • Who uses it: a project scheduler/PM who currently finds out about a slip only after it's already happened.

④ Supply Chain Visibility & Risk

  • What it does: tracks equipment shipments (transformers, generators, chillers — the big long-lead-time items) across multiple tiers of suppliers, flags ones at risk of arriving late, figures out the root cause, and even checks whether the equipment's spec sheet itself meets the governing standard (e.g. IS 8623-1 for switchgear).
  • Output: severity-tiered alerts with the evidence behind each one, linkable straight to the shipment/document that triggered it.
  • Who uses it: a procurement/logistics manager juggling dozens of shipments from multiple countries.

⑤ Commissioning QA

  • What it does: ingests real equipment test-log data (currently: cooling-system logs) and checks every reading against an engineering "envelope" (allowable operating range) — pass, fail, or "allowable but flagged" — producing NCRs and a full as-commissioned quality package, the same kind of document normally assembled by hand at project handover.
  • Scope right now: the cooling/HVAC slice is fully built; electrical and fire commissioning are noted as a future extension (there just wasn't good enough real test-log data available to build them credibly yet).
  • Who uses it: a commissioning engineer, at the point where a system is being signed off as ready for operation.

4 · How a verdict actually gets decided (tiered verdicts)

This is the newest and most important upgrade to the core idea (built during the HexaFalls phase). Originally, every single check needed someone to hand-write the rule in code ahead of time. That doesn't scale to the thousands of clauses across dozens of Indian standards. So there are now two tiers:

TierWhen it appliesWho decides the verdictHow it's shown
Certified A parameter that someone has already hand-written a rule for Hand-vetted Python code (unchanged from day one) Green badge: "Certified · pre-vetted"
Computed-draft No hand-written rule exists for this parameter yet The AI reads the real clause and writes down what the rule IS (as structured data, not a verdict) — then a small, separate, sandboxed piece of code computes the actual pass/fail from that Amber badge: "DRAFT · confirm reading" — an engineer must sign off
Unresolved Nothing confident enough was found, or the AI's reading failed a safety check Nobody — it's honestly flagged as unresolved rather than guessed at Slate badge: "No governing clause found"
The key safety detail: in the computed-draft tier, the AI is only ever allowed to fill in a structured template (like: "this value must be ≥ this number, from this exact clause text"). It NEVER writes or runs its own math. A tiny, deliberately limited calculator (it can only do addition/subtraction/multiplication/division/min/max on known numbers — nothing else, no arbitrary code execution) does the actual computing. And before any of this is trusted, the system double-checks that the specific phrase the AI says it read really does appear, word-for-word, in the real clause text — if that check fails, the result is thrown out as "unresolved," not silently used anyway.

5 · The HexaFalls additions (sponsor tech)

These are new capabilities layered on top of the untouched core above. Every one of them is optional and off by default — the app works completely fine without any of them, which matters because it means a judge can run this with zero setup and still see the real thing.

Gemini — the AI's new default "brain" for reading/writing

  • Replaced Anthropic Claude as the default model that reads documents and writes the plain-English findings (Anthropic and a couple of others are still supported as alternatives).
  • Purely a "perceive and explain" role — see the core idea above. Swapping the model here changes nothing about how a verdict is decided.

Actian VectorAI DB — offline semantic search

  • The Copilot/Knowledge Base features need to search thousands of code-clause chunks by meaning, not just keyword — that's done with "embeddings" (turning text into a list of numbers that capture its meaning) and a "vector database" to search them fast.
  • The default engine for this keeps everything in the app's own memory (called "numpy" here). Actian is a real, separate, offline database that can do the same job — useful for a site that can't send its data over the internet at all (a genuinely realistic requirement for sensitive infrastructure projects).
  • Swapping to Actian changes nothing about what answers look like — same search, different engine underneath, which is exactly the point (it's a drop-in replacement).

MongoDB Atlas — the audit ledger

  • Every time the system finalizes a compliance decision, it's now recorded once, permanently, in a running log — an "audit ledger." Records are never edited or deleted, only added.
  • Each record carries a "content hash" — a unique fingerprint computed from its important fields (severity, citation, values — NOT the AI-written prose, which can legitimately reword itself between runs). If the underlying decision data changes later, the fingerprint no longer matches, and that mismatch is detectable.
  • If no MongoDB is configured, it quietly falls back to a plain local file doing the exact same job — the ledger always works, one way or the other.

Solana (blockchain) — the anti-corruption proof

  • This is the single most concrete "we can prove nobody quietly changed a record" feature in the whole project.
  • Take a ledger record's fingerprint (from above) and write it into a tiny, real transaction on the Solana blockchain (a test network called "devnet" — no real money involved). Blockchains are designed so that once something is written, it can't be secretly edited or erased by anyone, including SiteMind itself.
  • The demo that makes this land: anchor a record's fingerprint on-chain, prove it with a public link anyone can check → then someone edits that record's data directly in the database, simulating tampering → the system re-checks and shows the LOCAL record no longer matches its own fingerprint, WHILE the blockchain independently confirms what the original, real fingerprint was. You don't have to trust SiteMind's own database to catch the tampering.
  • Careful phrasing matters here: this is tamper-evident (you can prove something was altered after the fact), not "tamper-proof" in the sense of preventing a person from acting corruptly in the first place, or from simply choosing not to anchor a record at all.

Telegram + ElevenLabs — the field bot

  • A site engineer standing at a transformer yard, phone in hand, isn't going to open a laptop and type a question. This is a Telegram chat bot they can talk to instead — by text OR by sending a voice note, in Hindi, English, or another regional language.
  • The pipeline: voice note → ElevenLabs turns speech into text → if needed, the AI translates it to English → the same Copilot from Pillar ② answers it, with the same "abstain if not confident" honesty → the answer gets translated back → ElevenLabs turns THAT into a spoken voice clip → the engineer gets a voice reply plus the text plus a link to the real citation.
  • Out-of-scope questions still get an honest "I don't have a confident answer for that" instead of a made-up one — same discipline as the desktop Copilot, just reachable from a phone in the field.

LangGraph — the Copilot's conversational upgrade

  • The original Copilot answers ONE question at a time with no memory of what you asked before. This upgrade turns it into a real back-and-forth conversation that remembers context (so "what about the transformer?" as a follow-up actually makes sense) and can pull information from multiple pillars in one answer (e.g. "any open issues on this submittal, AND is the cooling equipment shipment delayed?" in a single question).
  • Important boundary: this is the ONLY place in the whole codebase where a general-purpose "AI agent framework" is allowed to run at all. Everywhere else in this project deliberately avoids that kind of framework, on purpose, because the verdict-deciding core needs to stay simple enough to audit line-by-line. This agent is only allowed to fetch already-computed, read-only information and phrase a cited answer from it — it is physically incapable of producing a new compliance verdict, because it has no access to that part of the codebase at all.

  • The browser never talks to anything except the backend — no direct calls to Gemini, MongoDB, or Solana from the UI. That single choke point is what keeps the whole system auditable and swappable.
  • Codebook is deliberately its own separate service — it's designed to be reusable by ANY AI agent (not just this app) as a standards lookup tool, using a standard called MCP (Model Context Protocol — a common way for AI tools to expose capabilities to AI agents).
  • Every external integration degrades gracefully. Unset a key, stop a service, or turn off a flag, and the app doesn't crash — it just falls back to the simplest version of itself (a local file instead of a database, the in-memory search instead of Actian, "disabled" instead of a blockchain anchor). This was a deliberate design rule applied consistently, not an accident.

8 · A day in the life — who uses this, and how

Morning: a structural design reviewer at the EPC contractor uploads the latest revision of a foundation shop drawing. SiteMind reads it in seconds, flags that the specified concrete cover is short of what IS 456 requires for this exposure condition, cites the exact clause, and drafts a Non-Conformance Report. The reviewer confirms it and sends it back to the contractor for revision — a check that used to mean manually flipping through a paper code book.

Midday: a site engineer standing at the transformer yard isn't sure what clearance distance is required. Rather than walk back to an office computer, they send a Hindi voice note to the project's Telegram bot and get a cited answer back as a spoken clip in seconds.

Afternoon: the project scheduler checks the Schedule Risk page and sees that a critical cabling activity is now flagged at risk because of a linked equipment shipment delay — traced back through Supply Chain Visibility to a specific supplier's customs hold. They use the suggested mitigation options to decide whether to expedite shipping or reshuffle the schedule.

Anytime, for an owner/auditor: anyone can open the Audit Ledger, pick any finalized decision, and verify — independent of trusting SiteMind's own database — that the record hasn't been quietly altered since it was made, by checking its hash against what's permanently anchored on a public blockchain.

9 · How to actually run it

  • Simplest path (no keys needed at all): cd backend && ./run.sh then cd frontend && npm install && npm run dev — Compliance and Commissioning QA work end-to-end offline, with deterministic templated prose instead of AI-written prose.
  • Full details, every flag, every optional key: see README.md at the repo root — it's kept accurate and is the single source of truth for exact run commands.
  • The HexaFalls additions (Actian, Mongo, Solana, the Telegram bot, the LangGraph copilot edge) each need their own env var turned on — none of them are needed to see the core product working.

11 · Glossary — every term you'll need

NCR (Non-Conformance Report)
A formal finding that something doesn't meet a required standard — the standard output of the Compliance pillar.
RFI (Request for Information)
A formal question one party on a construction project asks another — "does clause X apply here?" — logged and tracked like a ticket.
Clause
One specific, numbered rule inside a building code standard (e.g. "IS 456:2000, Clause 26.4.2.2").
Verdict / verdict tier
The pass/fail decision on one checked value, and which of the three tiers (certified / computed-draft / unresolved) produced it — see section 4.
Eval (evaluation script)
A re-runnable test that checks the system's actual behavior against a known-correct answer set, producing a real accuracy number — the ONLY source this project allows for any claimed metric.
Embeddings / vector search
Turning text into a list of numbers that captures its meaning, so a computer can find "similar meaning" text even when the wording is completely different.
Abstention
The system's deliberate choice to say "I don't have a confident answer" rather than guess — treated as a correct outcome, not a failure, when the confidence really is too low.
Content hash
A unique fingerprint computed from a record's important fields — changes if and only if the underlying data changes.
Devnet (Solana)
Solana's free public test network — real blockchain mechanics, zero real-money cost.
Flag / feature flag
An on/off switch (an environment variable) that turns an optional capability on — everything in this project defaults to OFF for anything that needs an external key/service.
MCP (Model Context Protocol)
A standard way for a piece of software to expose its capabilities so ANY AI agent can call them — what makes Codebook reusable outside this app.

12 · Known gaps (short version)

A full, honest audit of everything imperfect about the current build lives in docs/gaps.md.
