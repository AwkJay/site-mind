# Audit A3 — Commissioning QA, Knowledge Graph, Overview/Command Center

Scope: `backend/app/commissioning.py`, `commissioning_standards.py`, `kg.py`, `overview.py`,
`documents.py`, `clock.py`, `eval.py`, `trace_api.py`, `impact.py` (pulled in because `overview.py`
depends on it) + `frontend/app/commissioning/page.tsx`, `frontend/app/graph/page.tsx`,
`frontend/app/page.tsx`.

Method: live backend on `localhost:8000` exercised directly with `curl`/`python3`, cross-checked
against source. All commands below were actually run during this audit (not simulated).

---

## Summary verdict

All five routes in scope are genuinely **COMPUTED** — no hand-authored node/edge lists, no
hardcoded stat tiles, no cosmetic clock. The commissioning envelope, the KG, the Overview machine-
scale tiles, the eval hallucination rate, and the clock's downstream recompute all held up under
live testing. The corpus-limitation disclosures for commissioning are real and load-bearing.

However, three concrete problems were found, in descending order of severity:

1. **UI inconsistency (real bug, not cosmetic):** every Commissioning NCR renders a green
   "Certified · pre-vetted" `verdict_tier` badge next to a red "Cross-source · unverified"
   citation badge on the *same card* — because `commissioning.py`'s `_to_ncr()` never sets
   `verdict_tier`, so it silently defaults to `"certified"` (see `backend/app/schemas.py:74`).
   This directly contradicts the module's own stated integrity tier.
2. **The Knowledge Graph's per-element scoping is dead in practice on the live dataset.** The
   graph is a single connected component (37 nodes, 1 component, confirmed programmatically) so
   `GET /api/kg/{element_id}` returns the *identical whole graph* for every element_id tried —
   valid matches, near-misses, and pure garbage strings alike. The "returns the requested node's
   neighbourhood" claim in code comments and `docs/features.md` is true of the *code path* but not
   observable in the *current data*.
3. **`docs/features.md`'s stated `getJSON`/`postJSON` timeout (3.5s) is wrong** — the live code
   (`frontend/lib/api.ts:66`) uses `TIMEOUT_MS = 90000` (90s), explicitly to survive Render
   free-tier cold starts. Not in my file scope per se, but it's the shared fetch helper the
   Overview and Graph pages both depend on, so I flag it here.

None of these are fabrication — they're an unset-field default bug (#1) and an honest-but-untested
gap between "the code is capable of X" and "X is observable today" (#2).

## Frontend page behaviour

**`frontend/app/commissioning/page.tsx`** — upload-only UI, no auto-load. Calls
`ingestCommissioningLog()` (`frontend/lib/api.ts:390-412`), which has **no mock/offline fallback**:
if the backend is unreachable it throws `CommissioningUnavailableError` with an explicit
"there is no offline/mock fallback for this action" message (api.ts:399-403). This is the correct,
honest behaviour and matches the project's stated "never fabricate a real-file result" rule. Renders
the corpus-limitation banner unconditionally whenever a package exists (`page.tsx:161-167`) and
reuses the shared `NCRCard` for FAIL/WITHIN-ALLOWABLE findings (see Finding #1 above for the badge
bug this exposes).

**`frontend/app/graph/page.tsx`** — calls `getKg()` with **no argument**, so it defaults to
`elementId = "eq-tx"` (`frontend/lib/api.ts:138-139`). `"eq-tx"` does not match any real node
(the mock data's fictional IDs like `eq-tx`/`eq-crah` are not in the live graph), so this call
*always* hits the whole-graph fallback path server-side. The frontend's node-click "highlight
neighbourhood" interaction (`graph/page.tsx:73-94`) is a **client-side, in-browser** filter over the
one fetched graph — it never re-queries `/api/kg/{element_id}` per click. So the actual per-element
backend scoping (`GET /api/kg/{id}`) is never exercised by this page's normal user flow at all; only
the always-whole-graph fallback is. The panel's static label "Subgraph · Transformer foundation"
(`graph/page.tsx:107`) is a hardcoded caption, not derived from the fetched element.
If the backend is down, `getKg()` falls back to `mockKg` (`frontend/lib/mocks.ts:506-529`) — 10
entirely fictional nodes (`eq-tx`, `eq-crah`, `std-456-cover`, ...) — and the page has **no
`r.live` check**, so a dead backend renders fabricated graph data with zero on-screen indication
that it isn't live (confirmed: `grep '.live' frontend/app/graph/page.tsx` → no matches).

**`frontend/app/page.tsx` (Overview / Command Center)** — same silent-mock-fallback pattern: calls
`getOverview()`, `getRisks()`, `getSupplyChainRisks()`, `getDocuments()`, `getCostRisk()`,
`getTimeline()`, none of which check `.live` (confirmed via grep — 0 matches in this file). If the
backend is down every tile on this page (machine-scale strip, cumulative impact, cost-at-risk, next
decisions) silently renders `lib/mocks.ts` fixture numbers as if live. (For comparison,
`frontend/app/timeline/page.tsx:119` *does* call `setLive(r.live)` — so this pattern exists
elsewhere in the codebase but was not applied to Overview or Graph.)

## The 6 specific questions, answered

### 1. Commissioning ingest — per-row verdicts against a real thermal envelope

Confirmed live. Uploaded the actual sample file:

```
curl -s -F "file=@backend/data/project_docs/sample_commissioning_log.csv" localhost:8000/api/commissioning/ingest
```

Result: `pass_count:2, within_allowable_count:1, fail_count:2, not_checkable_count:1` across 6 rows,
matching hand-verification against the envelope table:
- CT-001 22.5°C supply air → PASS (recommended 18-27)
- CT-002 30.5°C → OUT_OF_RECOMMENDED_BUT_WITHIN_ALLOWABLE (outside 18-27, inside allowable 15-32) → NCR MEDIUM
- CT-003 34.0°C → FAIL (outside allowable 15-32) → NCR HIGH
- CT-004 48%RH → PASS (recommended 20-60)
- CT-005 88%RH → FAIL (outside allowable 8-80) → NCR HIGH
- CT-006 415V power → NOT_CHECKABLE (system != "cooling")

The envelope is defined in `backend/data/standards/commissioning_clauses.json`, loaded by
`backend/app/commissioning_standards.py:22-25` (`_load()`, `lru_cache`). It is **explicitly
disclosed as cross-source-compiled, not verified**: the file's own `_note` field states — verbatim,
confirmed by reading the file — "PARTIAL, CROSS-SOURCE CORPUS — NOT the same integrity bar as
clauses.json (manak)... The primary ASHRAE book is commercially sold, not freely fetchable, and was
NOT independently verified against a single primary document," compiled from one official ASHRAE
free white paper cross-checked against 3 secondary sources. Every clause row carries
`"source_type": "cross_source_unverified"`. `commissioning.py`'s own module docstring
(lines 9-13) repeats this disclosure. The humidity check is further disclosed as a
"SIMPLIFIED" flattening of ASHRAE's true dew-point+RH% criterion — also stated in the `_note` and
in a separate `known_simplification` field. This disclosure is real, not just present in a docstring
nobody reads: it is threaded into the API response (`corpus_limitation` field on every
`QualityPackage`) and rendered unconditionally in the frontend banner (`commissioning/page.tsx:161-167`).

### 2. Cooling-only slice — what happens to power/IT rows, does electrical/fire genuinely not exist

Confirmed. `check_record()` (`commissioning.py:90-91`) returns `NOT_CHECKABLE` immediately for any
`record.system != "cooling"` — proven live by CT-006 (system=power, voltage=415V) → `NOT_CHECKABLE`,
`citation: null`, no NCR. The row is **parsed and accepted**, never rejected/dropped — it just can't
be checked. `_CHECKABLE_PARAMS` (`commissioning.py:39`) further restricts checkable cooling
parameters to `supply_air_temp`/`return_air_temp`/`room_temp`/`relative_humidity`/`return_air_rh`/
`room_rh` only. There is no electrical/fire commissioning module anywhere in
`backend/app/` — grep and file listing confirm only `commissioning.py` + `commissioning_standards.py`
exist for this pillar, and `commissioning_clauses.json`'s `_note` explicitly states "no electrical,
fire, or DG-set commissioning coverage" and points at `sitemind/docs/codes.txt` for what's still
needed. This matches the "cooling-only slice" framing everywhere it's claimed.

### 3. Knowledge Graph — real structured data vs. hand-authored; genuinely different neighborhoods?

**Built from real structured data — confirmed by code and by data-shape.** `kg.py:22-78`
(`_graph()`) builds the graph from `load_submittal_params()` (parsed from
`backend/data/project_docs/design_basis_params.json`, 11 real structural params, confirmed by direct
read), `load_submittals()` titles, `applicable_checks()` (the same rule-selection function
Compliance uses — imported from `.agents.checks`, not a separate/duplicated list) to derive
`governed_by` edges, and `load_rfi_log()` with a regex-based shared-4-digit-sequence match to link
RFIs to specs. Nothing in `kg.py` is a literal node/edge list. This is genuinely computed, and the
"IS 1893 Cl. 7.2.3" / clause-citation edges resolve to the same `standards.get_clause()` used
elsewhere in the app — not a separate fabricated set.

**But: querying different `element_id`s does NOT return genuinely different neighborhoods on the
live dataset — verified programmatically, not just by inspection.** Ran the graph builder directly:

```
total nodes: 37  edges: 44
connected components: 1
```

One connected component containing all 37 nodes. Consequently every query tried — a real node
("Footing F-12" URL-encoded), a syntactically-close-but-wrong string ("footing-f-12", hyphen vs.
space), an unrelated real submittal ID ("DC1-16-SD-0931-R0"), and pure garbage
("does-not-exist", "zzz-no-match-at-all") — **all returned the identical 37-node, 44-edge graph.**
Root cause: `kg.py:76-77`'s RFI-linking fallback (`if not linked and doc_seqs: g.add_edge(rfi_node,
next(iter(doc_seqs)), label="references")`) attaches every unmatched RFI to an arbitrary doc, which
merges what would otherwise be separate clusters into one component, given how few
docs/RFIs/params exist in this dataset (11 params, all structural; 12 docs; RFIs across
structural/electrical/mechanical/architectural disciplines but no non-structural equipment/spec
nodes to anchor to). Separately: `load_design_basis_params()` currently contains **zero**
electrical/mechanical/fire elements — every equipment node in the graph is structural (Footing F-12,
Column C-08, etc.) despite the project's Compliance pillar being described elsewhere as "Structural +
electrical domains." The graph itself is structural-only today.

So: the *code path* (`_serialize(keep)` after `node_connected_component`) is real and would
produce a genuinely smaller subgraph on a less-connected dataset — this is not a hardcoded
whole-graph return — but on the actual live data, the neighbourhood-scoping feature is
**inert**: it degenerates to "always return everything" for every input tried.

### 4. Overview — 4 stat tiles, "Next decisions," cumulative-impact/ROI

**Machine-scale tiles are computed, not constants.** `overview.py:55-88`:
- `documents_read = len(load_submittals())` — real submittal count.
- `clauses_checked = sum(r.coverage.clauses_cited for r in results if r.coverage)` — summed across
  live `evaluate()` runs over the Design Basis Report(s).
- `cross_references_found = sum(1 for s in supply_chain_shipments() if s.linked_rfi is not None)` —
  counts genuinely-matched (curated or TF-IDF-retrieved) RFI links, not the near-automatic
  WBS-activity join (the code comment at `overview.py:68-72` explicitly explains why it picked the
  more selective signal).
- `conflicts_surfaced = sum(len(r.overlaps) for r in results)` — real multi-clause-governance
  overlaps from the compliance runs.
Live value confirmed via `curl localhost:8000/api/overview`:
`{"documents_read":12,"clauses_checked":12,"cross_references_found":5,"conflicts_surfaced":2}`.

**"Next decisions" ranking is computed client-side, not server-asserted.**
`frontend/app/page.tsx:40-76` (`buildDecisionItems`) merges `SupplyChainRisk.recommended_alternative`
windows and `RiskItem`s that are `on_critical_path && project_impact_days > 0`, sorts by urgency, and
takes the top 3. The code comment states (and the implementation matches) that it "computes no new
business logic" — every field traces to an existing backend-computed value.

**Cumulative-impact/ROI figures are computed, but rest on labeled, non-measured assumptions —
same caveat the project's own CLAUDE.md flags.** `overview.py:64,77-78` sums
`impact.all_pillar_impacts(issues)`, each of which multiplies a real live signal (open-NCR count,
schedule-flag count + critical-path days, at-risk-shipment count + days-at-risk, commissioning FAIL/
within-allowable counts from actually running the *real* sample commissioning log through
`build_quality_package()` — `impact.py:62-77`, confirmed this is the real pipeline, not an invented
number) by a **stated, hand-picked constant** (`impact.py:31-59`, e.g. "20 engineer-hours per NCR,"
"Rs 15,00,000 rework per issue," "Rs 50,000/day coordination overhead") — every constant is
disclosed inline in the `basis` string returned to the client, never hidden. This matches the
project's own "ROI figures are assumption-based... always say the assumption out loud" rule. Nothing
here is fabricated, but nothing here is measured either — it's arithmetic over disclosed multipliers.

### 5. `GET /api/eval/report` — live re-verification, auto-run, hallucination rate

**Hallucination rate is live-recomputed on every request, not read from a file.**
`eval.py:22-47` (`_hallucination_rate()`) calls `evaluate(doc)` for every submittal, walks every
NCR's citation, and checks it resolves against `get_clause()` over `_ALL_KEYS` (all real clause
keys from `all_clauses()`). Live value: `curl localhost:8000/api/eval/report` →
`"hallucination_rate":0.0,"hallucination_detail":"0/11 cited clauses unresolved (live agent output)"`.
This is a genuine live check, confirmed by reading the loop, not an asserted constant.

**Auto-run behaviour: present in code, but NOT exercised in this audit.** `eval.py:86-93`
does `if not report_path.exists(): subprocess.run([sys.executable, "-m", "eval.run_eval"], ...)`. On
this run, `backend/eval/report.json` already existed (dated 2026-07-25 01:15, from an earlier
session), so this branch was never triggered live during my test — **UNVERIFIED live behaviour**
(the code path reads correctly, and matches the docstring claim, but I did not force the missing-file
state to watch it actually regenerate, to avoid disrupting a shared live backend other audits may be
using concurrently).

**Per-class metrics (`macro_f1`, `accuracy`, `confusion_matrix`, `baseline`) come from the
pre-generated `backend/eval/report.json` FIXTURE**, not recomputed per-request — but that file is
itself the output of a real script (`backend/eval/run_eval.py`) run against
`backend/eval/testset.jsonl`, not hand-authored. Live values: `macro_f1: 1.0, accuracy: 1.0`, n=41,
confusion matrix `[[16,0,0],[0,16,0],[0,0,9]]` (i.e., zero misclassifications on this labelled set) —
plausible for a deterministic rule engine against its own boundary-case test set, but I did not
independently re-derive this number from `testset.jsonl`, so treat the *exact* F1/accuracy figures
as read-from-fixture, verified only for internal consistency (file exists, is well-formed, is what
the endpoint serves), not independently re-run by me.

### 6. Simulated clock — does advancing it actually invalidate caches and recompute?

**Confirmed live, not cosmetic.** Sequence actually run:
```
GET  /api/overview          → schedule_at_risk: 6
POST /api/clock/advance {"days": 45}  → {"current_day":220,"offset_days":45}
GET  /api/overview          → schedule_at_risk: 13
POST /api/clock/reset       → {"current_day":175,"offset_days":0}
GET  /api/overview          → schedule_at_risk: 6
```
`schedule_at_risk` genuinely changed (6 → 13 → 6) as a direct result of advancing/resetting the
clock — no other input changed. This traces to `clock.py:40-57` (`_clear_downstream_caches()`),
which explicitly `cache_clear()`s `schedule.risks`, `supply_chain.shipments/risks/alerts`, and
`timeline.all_events` — all `lru_cache(maxsize=1)` functions whose output depends on
`current_day()`. `_offset_days` is the only mutable state in the module (in-memory, resets on server
restart), and `MAX_OFFSET_DAYS = 60` clamps the range. This is real, verified cache invalidation +
recomputation, not a cosmetic ticker.

## Stale-or-wrong claims found in `docs/features.md`

1. **Timeout claim (line 290-291, "Cross-cutting frontend conventions"):** states `getJSON`/
   `postJSON` use "3.5s timeout." **Wrong** — live code (`frontend/lib/api.ts:66`) is
   `TIMEOUT_MS = 90000` (90 seconds), with a code comment explaining this was deliberately raised to
   survive Render free-tier cold starts (measured ~52-72s). Codebook-specific calls use
   `CODEBOOK_TIMEOUT_MS = 180000` (180s). This is a real, checkable drift between docs and code —
   whoever wrote "3.5s" was describing an earlier version of this constant.
2. **KG section (line 141-147)** is accurate about *mechanism* ("builds an in-memory graph from
   `applicable_checks()` and shared-ID RFI references, returns the requested node's neighborhood
   (or whole graph on no match)") but doesn't disclose that on the live dataset this degenerates to
   "always whole graph" for every input (see Q3 above) — not false, but gives a stronger impression
   of demonstrable per-node scoping than the current data supports.
3. **"Surfaced to callers via a `live: boolean`" (line 291)** is true of the API shape but
   overstates UI behaviour — only `frontend/app/timeline/page.tsx` actually reads and displays
   `.live`; Overview and Graph (both in this audit's scope) fetch via the same helper but never
   check `.live`, so a dead backend on those two pages silently shows fixture/mock numbers with no
   on-screen "offline" indicator. `docs/features.md` doesn't distinguish which pages actually wire
   this up.
4. No claim found in `docs/features.md` about commissioning's `verdict_tier` defaulting
   incorrectly — this UI bug (Finding #1 above) isn't mentioned anywhere in the docs I checked, so
   it's not a case of stale docs, just an undocumented/unnoticed inconsistency.
