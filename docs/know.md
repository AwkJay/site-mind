# Know this before you demo — where the data comes from, and how to answer judges

This file exists so you (not just judges) fully understand what's real, what's synthetic,
and why — in plain language, no jargon left unexplained. Read this once and you should be
able to answer almost any question a judge throws at you about where this data is "from."

Backing research (web-searched, with links) lives in `know/market-research-findings.md` —
this file is the short, judge-ready version of that research.

---

## 1. The one-sentence answer

**SiteMind is a real, working piece of software applied to a realistic-but-invented
scenario** — a hackathon build, not a deployed product at a real company. The engineering
(the code, the AI pipeline, the standards-checking logic) is 100% real and functional.
The *project* it's checking (a specific data centre in Chennai with specific documents,
RFIs, and a specific schedule) is synthetic — invented for this demo, not a real client's
actual jobsite.

## 2. Real vs synthetic — the honest breakdown

| Thing | Real or synthetic? | Why |
|---|---|---|
| The Indian standards cited (IS 456, IS 1893, IS 875, IS 3043, IS 732, IS 8623, CEA 2010) | **REAL** | Genuine, currently-in-force Bureau of Indian Standards (BIS) / Central Electricity Authority codes. Verified against the BIS's own website and the Internet Archive. |
| The exact clause text shown for each citation | **REAL** | Digitised verbatim from the real standard documents (some from clean native PDFs, some OCR'd from scanned copies — the app discloses which, per clause). |
| The checking/verdict logic (pass/fail math) | **REAL** | Deterministic Python — every verdict is computed, not guessed by an AI. See `docs/ARCHITECTURE.md`. |
| The AI/LLM pipeline (extraction, prose, chat) | **REAL** | Actually calls Gemini live; genuinely does the extraction/reasoning described. |
| Chennai as a hyperscale data-centre hub | **REAL trend** | Chennai is currently one of India's two biggest data-centre markets (with Mumbai) — see the table in `know/market-research-findings.md` for 7+ real, named, currently-under-construction projects there. |
| "48 MW, Tier III, concurrently maintainable, N+1" | **Realistic, representative** | Sits right in the middle of real announced Chennai projects (24MW-216MW range). Tier III/N+1 is a real Uptime Institute classification, not invented. This specific number wasn't copied from one specific real project — it's a plausible composite. |
| The specific project itself — its documents, RFIs, NCRs, schedule, supply chain | **SYNTHETIC** | Generated by `backend/data/gen_synthetic.py` for this demo. No real company's actual project data was used. |
| ROI figures (~20 engineer-hours, ~₹15L saved per issue) | **Labelled assumption** | Stated as an assumption in the app itself, not a measured outcome. Never present these as a forecast. |
| "Design Basis Report / RFI / Submittal / NCR" as a workflow | **REAL industry practice** | Standard construction/EPC vocabulary used on any large infrastructure project worldwide — not data-centre-specific, not invented for this demo. |

## 3. "Where did this specific scenario come from?"

SiteMind was originally built for the **ET AI Hackathon 2026, Problem #4 — "AI
Intelligence Platform for Data-Centre EPC Project Delivery."** That's a real, currently
running hackathon. The problem statement asked for an AI platform that helps run a
data-centre construction project (compliance checking, RFI/schedule/supply-chain
intelligence, commissioning QA) — data centres were the *given* domain, not something we
picked. We then had to invent a believable project to build and demo against, since no
real client's actual project data was available (nor would it be appropriate to use one
without permission). Chennai + 48MW + Tier III was chosen because it's realistic (see the
table above), not because it's copied from one real, named site.

The project was later repositioned for the **HexaFalls** hackathon (an open-innovation
event) — see `hexafalls_plan.md` for why, and the additive sponsor-tech integrations
(Actian, MongoDB, Solana, Telegram+ElevenLabs, LangGraph) that came with that pivot.

## 4. Anticipated judge questions — direct answers

**"Is this a real client's project?"**
No. It's a synthetic, representative scenario modelled on real market conditions (see §2).
We say this proactively, every time — the app itself discloses it (see the Settings panel
and README).

**"Then why should I trust the compliance verdicts?"**
Because the *standards* and the *checking logic* are real, even though the *project being
checked* is synthetic. Feed this system a real Design Basis Report tomorrow and it checks
it against the same real IS 456/1893/875/etc. clauses with the same deterministic Python
— nothing about the verdict math is scenario-specific.

**"Why data centres specifically?"**
That was the given hackathon problem domain (ET AI Hackathon Problem #4), not a choice we
made independently. That said, data centres are a genuinely good fit: they're megaprojects
with heavy compliance burden, tight schedules, and (per our research) Chennai/India is
currently in a real hyperscale data-centre construction boom — so the domain is timely,
not arbitrary.

**"Could this work for other kinds of megaprojects?"**
Yes — the compliance/schedule/supply-chain/commissioning logic isn't data-centre-specific;
it's generic "check documents against cited standards, track schedule risk, track supply
chain, track commissioning test results." The HexaFalls repositioning explicitly broadens
the framing to "any hyperscale/public-infra megaproject."

**"Are the standards citations clickable/verifiable?"**
Yes — every citation resolves to a real source. Most link straight to the exact standard
on the Internet Archive (e.g. `archive.org/details/gov.in.is.456.2000`, a real, publicly
verifiable BIS document). Click "View standard" on any citation in the app to see the
actual verbatim source document open in a viewer, not just a link.

**"Did an AI make up any of the standards or their text?"**
No — this is the core integrity rule of the whole project (see `.claude/CLAUDE.md`'s
"non-negotiable integrity rules"). The LLM never invents a clause; every citation is
pre-digitised, real text. The LLM's role is prose/reasoning, never fact invention.

**"How much of this is 'just an LLM wrapper'?"**
Very little of the decision-making. Every pass/fail verdict is computed by plain Python
against a cited rule — the LLM's role is (a) extracting values from a document with their
exact source location, (b) for un-vetted clauses, reading a rule's *shape* out of the real
clause text (which Python then computes), and (c) writing prose/summaries/chat answers.
See `docs/ARCHITECTURE.md`'s "why no agent framework in the verdict core" section.

**"What's still rough / not fully done?"**
We keep an honest running list in `docs/gaps.md` — worth skimming before a demo so nothing
surprises you. Nothing on that list is hidden; it's there specifically so you can speak to
it confidently if asked.

## 5. If you get a question you genuinely can't answer

Say so, and point at the actual source: "the standards and the checking logic are real
and I can show you exactly where; the demo project itself is a synthetic scenario we
built, disclosed in the app — happy to dig into any specific number's exact code path."
That's a strong, honest answer for any hackathon — judges respect a team that knows
precisely what's real, what's representative, and why, over a team that oversells.
