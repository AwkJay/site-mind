## 1. The core credibility thesis (the moat — do not weaken)

- **The LLM never *computes a verdict*.** Pass/fail is deterministic Python against a
  **real, cited primary-source code clause** (`checks.py` + `clauses.json`).
- **Never invent a clause.** Every citation resolves to real digitised IS / BIS / CEA text.
- **No asserted numbers.** Every metric comes from a real eval run (`backend/eval/`).
- **OFFLINE_MODE boots with zero keys.** Every new integration is additive and degrades to
  a clean no-op. The keyless demo path must never break.
- **Evals stay byte-identical.** New backends are opt-in via env flags; default = safe/offline.

**The plain-English version of the thesis (how one check runs):**
1. **READ** (AI) — reads the messy PDF, pulls the value (e.g. "40mm cover"), points to the
   exact sentence. Value kept only if its quote is a verbatim substring of the source, else dropped.
2. **JUDGE** (plain code) — runs one comparison: `40 < 50` → FAIL. No AI. Just math.
3. **WRITE** (AI) — writes the human explanation prose.
So "the LLM never decides" = the LLM never does step 2. It's a calculator, not a brain.
`40 < 50` is the same answer forever and points to the exact clause → auditable. An AI verdict
= "flagged because vibes" → a regulator can't certify that.

Today the AI touches only **2 of the 10 sidebar pages** (Compliance = read docs + write findings;
Copilot = write answers). Everything else is pure code/math. Knowledge Base / Codebook use
embedding "smart search", not a generative LLM.

## 3. Session 2 — the BIG evolution: tiered compliance verdicts

The user pushed back hard and correctly on a scaling weakness:

> *"There are **thousands** of clauses, tables, formulae in IS standards. We can't hand-write
> Python (`if/else`) for every one. Use hybrid RAG, cite the source, show the model's **draft
> verdict** + **how it decided**, make it easy for an engineer to verify against the source, then
> the engineer makes the final call — double-checking."*

This resolved the tension between **"scaling needs LLM reasoning"** and **"auditability needs
determinism"** via **structured-rule extraction + a generic evaluator**.

### The three verdict tiers (all cite a real clause) — new `NCR.verdict_tier` field

| Tier | When | Verdict computed by | UI badge |
|---|---|---|---|
| 🟢 `certified` | Param matches one of the ~17 hand-vetted rules in `checks.py` | hand-vetted Python (unchanged) | "Certified · pre-vetted" (green) |
| 🟡 `computed_draft` | No `checks.py` rule → retrieve clause → **LLM extracts a structured rule** → **generic Python evaluator computes** | Python evaluator; LLM only *read* the rule | "DRAFT · confirm reading" (amber) |
| ⚪ `unresolved` | Retrieval abstains, or the rule phrase fails the substring gate | none — honestly flagged | "No governing clause found" (slate) |

### How the "math" is actually checked (critical — NO code generation, NO math-subagent)

1. The LLM reads the **retrieved, real** clause and outputs a **structured rule as JSON**
   (`ExtractedRule`: `kind` = compare / range / min_of / max_of / table_lookup / formula / none;
   operator, threshold, unit, inputs, table, expression, `clause_phrase`, `clause_key`). It is
   *describing* the rule, **not calculating**.
2. A pre-written generic evaluator `rule_eval.py` does the arithmetic — same reviewed code every
   time. **No subagent writes code. No `eval()`/`exec`.**
3. For formulae: a **safe AST evaluator** with a strict whitelist (numbers, named inputs,
   `+ - * / ** ( )`, `min`/`max` only). Rejects anything else. Never raises.
4. The UI shows **value + rule + math + cited clause side-by-side** as a **DRAFT** a licensed
   engineer confirms (`status="REVIEW_REQUIRED"`).

### Two anti-hallucination gates (non-negotiable)
1. The extracted **value** already passes `verify_spans` (verbatim quote from the uploaded doc).
2. The extracted rule's **`clause_phrase` must be a verbatim substring of the retrieved clause
   `raw_text`** (reuse `llm_extract._norm` substring logic). Fail → `unresolved`. Never fabricate.

### The key mental model
*"Reasoning text ≠ proof; the cited clause is the proof."* Two halves: **Interpretation**
(LLM, fallible, verified against source in ~5s by the engineer) vs **Computation** (deterministic
code, always correct). The thesis shifts from *"the LLM never decides"* to
**"the LLM never *computes a verdict*"** — it reads, code computes, engineer confirms.

**The seam this attaches to:** `compliance.py:282-283` `if not applied: continue` — today an
unmatched param is silently dropped (a blind spot). The new tier fills it, **behind a
default-off flag** (`COMPLIANCE_RULE_EXTRACTION`), so evals stay byte-identical. **If the clock
runs out:** ship the seam + two-half UI with a hand-written `ExtractedRule` fixture for the demo
clause; LLM extraction is the scale *proof*, not the foundation.

## 4. Session 2 — the framework question (Copilot edge)

The user asked how "just Gemini" handles tool-calling / memory / scale in production, since judges
probe this. Two weapons were developed:

**The reframe (offensive, not defensive):** frameworks like LangGraph/ADK put the *LLM in charge
of control flow* — the model picks the next step at runtime. Compliance can't have an unauditable
decision path (a regulator can't certify it). So we inverted it: **the model perceives and
explains; orchestration is deterministic Python you can read, test, diff, version.**

**What the LLM MAY decide** (perception / navigation / expression): what to extract, which
tool/corpus to search, how to phrase, whether it's confident enough to answer.
**What the LLM MUST NOT decide** (adjudication): the pass/fail verdict, which clause governs, the
threshold comparison, whether something is compliant.

**"Memory" = 4 purpose-built layers, not one framework wrapper:** Actian (semantic recall) ·
MongoDB (conversation history + facts) · Solana (tamper-proof provenance) · Gemini's native
multi-turn API (short-term conversation). Chat without a framework = Gemini is natively multi-turn,
you just persist the message list in Mongo (that IS what LangChain "memory" does internally).
Agents without a framework = Gemini function-calling for tool routing + MCP (Codebook already
speaks it). Scale = stateless FastAPI workers, state in Atlas/Actian/Solana, no orchestration
bottleneck by design. Be nuanced, not dogmatic: *"ADK would be fine for the chat layer; never the
decision layer."*

**Resolution after back-and-forth (user was explicit: NOT chasing the Google/ADK prize — "use
whatever is better for future scaling like LangChain or LangGraph"):**
- **NO framework in the verdict core** — `checks.py`, `rule_eval.py`, the compliance pipeline stay
  pure, auditable Python.
- **LangGraph allowed ONLY on the Copilot conversational edge** (chat page + Telegram bot). It
  routes questions, calls **read-only** tools wrapping existing pillar endpoints, phrases cited
  answers — **never** makes a pass/fail decision. Chosen over LangChain legacy agents because it's
  an explicit graph/state-machine (control flow stays inspectable, fits auditability) + ships
  durable checkpointers for memory. Confirm the current LangGraph API at build time.
- **Memory:** a LangGraph **Mongo checkpointer** keyed by `thread_id` — replaces any hand-rolled
  history collection.
- Gated on `COPILOT_AGENT_ENABLED` (default 0) + present `GEMINI_API_KEY`; lazy import; **keyless
  boot falls back to the existing cited-RAG `copilot.answer()`** so the app always boots offline.

**Two agreed Copilot/bot upgrades (from the "will the bot know the project?" discussion):**
1. **Chat memory (Mongo)** — so the bot remembers the conversation ("what about the transformer?"
   resolves the reference). Small, definitely do it.
2. **Project-brain bot** — reaches ALL pillars (compliance/schedule/supply-chain), not just docs,
   via safe tool-routing (picking *where to look* is allowed; only judging is forbidden). Turns a
   Telegram search box into "ask my project anything, by voice, in Hindi, from the field."
